# .ion format version 0 — metadata layout changes from v1

This document describes only what changed for `format_version = 0` versus
[`v1.md`](v1.md). Everything not mentioned here (header layout, A/B window
directories, block containers, summary/entries/array-address sections, CV
codes, integrity rules) is unchanged. Read `v1.md` first.

## 1. Version is the current writer default; v1 stays readable

`format_version` is a `u16` at header byte 9 (`HEADER_FORMAT_VERSION_OFFSET`,
`crates/parser/src/ion/header.rs`), written little-endian, right after the
8-byte file signature `IONIC\0\0\0` (bytes 0..8) and the 1-byte endianness
flag (byte 8, always `0`). The file signature is still checked first and
guards blank/empty files exactly as in v1: `Header::parse` rejects the file
before it even looks at the version byte if the signature does not match.

`crates/parser/src/ion/version_generated.rs` (generated by `make sync`, do
not hand-edit) defines:

```
CURRENT_VERSION        = 0
MIN_SUPPORTED_VERSION  = 0
MAX_SUPPORTED_VERSION  = 1
```

`Header::write` always stamps `CURRENT_VERSION` (0) — the writer no longer
produces v1 files. `Header::parse` accepts both 0 and 1 (`allow_version`,
`format.rs`), so a v1 file written by an older build still decodes
correctly. Version 1 is legacy-read-only; version 0 is the only format the
encoder emits going forward. A version outside `0..=1` is a hard read error
(`IonError::UnsupportedFormatVersion`), same policy as v1.

## 2. C / D / E metadata column order in v0 (VI and VOFF are gone)

Sections C (spectrum metadata), D (chromatogram metadata), and E (global
metadata) keep the same group/section framing as v1 (group directory,
12-byte group header of `meta_count`, `numeric_count`, `string_count`, C is
still grouped in fixed groups of `metadata group size` = 8192 items with
group-local value pools; E is still one ungrouped section with the same
32-byte counts header). What changes is the column list inside a group (or
E section) body.

v1 column order (10 index/attribute columns, `n` = row count, `g` = items
in the group):

```
CI  MOI  MPI  MTI  MRI  MAN  MURI  MUAN  VK  VI  VN  VOFF  VLEN  VS
```

v0 drops **`VI` (value indices)** and **`VOFF` (string offsets)**. The v0
column order, written by `serialize_group` (spectra/chromatograms,
`crates/parser/src/ion/encoder/utilities/meta_collector/grouper.rs`) and
`write_packed_meta` (global E, same file), is:

| Column | Type | Length | Meaning |
| ------ | ---- | ------ | ------- |
| `CI` local index offsets | u32 | g + 1 | row slice `CI[i]..CI[i+1]` for item `i` — unchanged from v1 |
| `MOI` owner ids | u32 | n | owner node id — unchanged from v1 |
| `MPI` parent ids | u32 | n | parent node id — unchanged from v1, but see §4 for what the stored values mean in v0 |
| `MTI` tag ids | u8 | n | unchanged |
| `MRI` CV ref codes | u8 | n | unchanged |
| `MAN` CV accession numbers | u32 | n | unchanged |
| `MURI` unit CV ref codes | u8 | n | unchanged |
| `MUAN` unit CV accession numbers | u32 | n | unchanged |
| `VK` value kinds | u8 | n | unchanged: `0` numeric, `1` string, `2` empty |
| `VN` numeric values | f64 | numeric_count | pool of f64 values, in row encounter order — **not indexed by a stored `VI`; see §3** |
| `VLEN` string lengths | u32 | string_count | byte length of each string, in row encounter order |
| `VS` string bytes | u8 | sum of string lengths | concatenated UTF-8 bytes, in the same row order as `VLEN` |

`VI` and `VOFF` are absent from the byte stream entirely — no placeholder,
no zero-fill. Every other column, and the section framing around it
(group directory, group header, compression), is byte-identical in shape
to v1.

## 3. Deriving VI and VOFF at read time

The decoder never needs the two dropped columns as stored data — it
recomputes them from what v0 *does* store, in the group's prologue, before
building any `Metadatum`. This lives in
`crates/parser/src/ion/decoder/utilities/parse_metadata.rs`, gated by
`MetaColumnLayout` (`.../decoder/utilities/meta_column_layout.rs`):
`MetaColumnLayout::from_version(0)` sets `vi_present = false` and
`voff_present = false`; `from_version(1)` sets both `true` so a legacy file
still reads its own stored `VI`/`VOFF` columns unchanged.

**Rule 1 — `VI` is a running per-kind counter over `VK`.** Walk the rows
`0..n` in order. Keep two counters, `next_numeric` and `next_string`, both
starting at 0. For row `i`:

- `VK[i] == 0` (numeric): `VI[i] = next_numeric`, then `next_numeric += 1`.
- `VK[i] == 1` (string): `VI[i] = next_string`, then `next_string += 1`.
- `VK[i] == 2` (empty): `VI[i] = 0` (unused; no pool to index).

(`rebuild_value_indices`.) This reproduces exactly what the v1 encoder
would have written, because the encoder appends to `numeric_values` /
`string_offsets` in the same row order it emits `VK`.

**Rule 2 — `VOFF` is the prefix sum of `VLEN`.** `VOFF[0] = 0`; for
`k >= 1`, `VOFF[k] = VOFF[k-1] + VLEN[k-1]` (`rebuild_string_offsets`).
`VS` is then read the same way as in v1: a string row reads
`VS[VOFF[VI] : VOFF[VI] + VLEN[VI]]`.

## 4. The normative invariant that makes the derivation legal

Both derivations are only correct because of one structural fact about how
the writer builds the value pools: **the value pool is strictly
row-parallel — exactly one pool entry per row of that kind, appended in
the same order the rows are encountered, with no deduplication and no
reordering.** `serialize_group` builds `numeric_values` and
`string_offsets`/`string_bytes` by iterating rows `row_start..row_end` once
and pushing to the matching pool on every numeric/string row it sees
(`grouper.rs:134-154`); it never looks up an existing pool entry to reuse
it. That is exactly what lets Rule 1 reconstruct `VI` as a plain counter
and Rule 2 reconstruct `VOFF` as a plain prefix sum, with no lookup table
needed at write time or read time.

**This is normative, not incidental.** If a future writer changes the pool
so that two rows with the same value share one pool entry (deduplication),
`VI` is no longer a per-kind running counter — it becomes real data that
must be stored again. That is a different on-disk layout and requires a
new `format_version`; it cannot be folded into v0's decoder as another
`MetaColumnLayout` flag, because the "recompute from `VK`" rule would
silently produce wrong indices instead of failing.

## 5. Per-item node-id reset and the group-unique remap

**Encoder (C/D only): every item's local node ids start over at 2.**
`TraversalContext::reset_for_item` (`meta_collector/mod.rs`) is called
unconditionally at the top of `MetaCollector::add_item`, for every spectrum
and every chromatogram — not just the first item in a group. It resets the
node-id counter to `FIRST_LOCAL_ITEM_NODE_ID` (2). The shared list node
(the `<spectrumList>`/`<chromatogramList>` element itself) keeps id `1` and
is only touched once, on the first item of a group
(`is_first_item_in_group()` still gates `writer.touch(list_tag, ...)`). So
within one group, item 0's metadata rows use ids `2, 3, 4, …`, item 1's
metadata rows *also* use ids starting at `2`, and so on — ids are no
longer unique across items in the same group, only unique within one item
(plus the shared `1`).

**Decoder (C/D only): ids are remapped to group-unique ids in the
prologue.** `MetaColumnLayout::ids_reset` is `true` for v0's C/D reader
(`from_version(0)`), so `parse_metadata` calls
`restore_group_unique_ids` right after `validate_children_index` and
before building any `Metadatum`:

1. `stride = 1 + max(every stored MOI value, every stored MPI value)` over
   the whole group (one `max` over both id columns).
2. For item `i` (0-based, found via the `CI`/`children_index` row range),
   `item_base = i * stride` (checked multiply).
3. Every id in that item's `MOI`/`MPI` rows is rewritten: if the local id
   is `1` (the shared list node), it is left as `1`; otherwise it becomes
   `item_base + local_id` (checked add).

This runs once per group, on both `MOI` and `MPI`, before the per-item row
loop that builds `Metadatum`s — so every downstream consumer (`to_mzml`,
`children_lookup`, the `spectra.rs` builders) sees the same group-unique,
tree-reconstructible ids it always did; the reset/remap is invisible past
`parse_metadata`'s prologue.

**The global E section is never reset and never remapped.**
`pack_global_meta` (`encoder/.../schema.rs`) writes E directly through
`context.alloc()` — it never calls `MetaCollector::add_item`, so
`reset_for_item` never runs for E and E's node ids keep accumulating across
the whole section exactly as in v1. On the decode side,
`IonReader::global_metadata()` (`decoder/decode/spectra.rs`) is the only
call site that reads E, and it explicitly builds its layout as
`MetaColumnLayout::from_version(header.format_version).without_ids_reset()`
— so even though `from_version(0)` would otherwise set `ids_reset = true`,
E always parses with `ids_reset = false` and its `MOI`/`MPI` values are
used as stored, unmodified.

`without_ids_reset()` only clears `ids_reset`; it leaves `vi_present` and
`voff_present` as `from_version` set them, so E still gets the v0
VI/VOFF-derivation behavior of §3 — only the id-remap step is skipped.
